# Go profile

How the Go modules meet the [repository's rules](../../docs/README.md). The rules
themselves live there; this profile maps them to Go, held the way Go does it: standard
library first, zero dependencies preferred.

## 1. Role and units

Go keeps servers and relying parties, their libraries and the ePA client
([architecture](../../docs/architecture.md#roles-of-the-languages)).

```text
 commands   cmd/zero-pdp  cmd/zero-pep-proxy  cmd/zero-bff-pdp  cmd/zero-epa  zero-caddy
              │  flags, env, files, secrets (*_PATH), logger, servers, signals
 servers    pdp/authzserver  pep/proxy  bff/gateway  epa/vau        (http.Handler)
              │
 libraries  oauth  oidf  dpop  nonce  gemidp  kv  store  brainpool  pkcs12  (no ambient I/O)
 adapters   sqlitestore                                             (a driver of their own)
```

- `main` and `cmd/` own the process: they read flags, environment and files, build the
  configuration structs, create the logger, the `*http.Client` and the stores, and wire
  them into handlers. Nothing below `cmd/` does that.
- Small interfaces, defined by the consumer: accept interfaces, return concrete types.
  The seams are the standard ones wherever they fit: `io.Reader`, `http.Handler`,
  `*http.Client` / `http.RoundTripper`, `crypto.Signer`, `crypto.Decrypter`,
  `*slog.Logger`, `context.Context`.
- `context.Context` is the first parameter of anything that does I/O or waits, and
  cancellation is honoured.

## 2. Sans I/O and transports

- A library reads no environment variable, flag or file it was not handed, uses no
  `http.DefaultClient`, starts no goroutine it cannot stop, and does not log except
  through a logger it was given. Configuration is a struct the command fills in; secrets
  arrive as `*_PATH` files read by the command.
- A client library takes an `*http.Client` (or an `http.RoundTripper`) and never builds
  its own TLS configuration or proxy policy; the command decides TLS, mutual TLS, proxies
  and timeouts. Tests pass `httptest.Server.Client()`. Where a protocol has non-HTTP
  transports (the VAU channel in `epa`), the core is written over `io.Reader`/`io.Writer`
  or a small interface, and the network sits in an adapter.
- Time comes in as a parameter or a `func() time.Time`; randomness from `crypto/rand`.
- TLS peer verification of TI endpoints is not the host's choice
  ([architecture](../../docs/architecture.md#the-host-owns-the-transport-the-core-owns-trust)):
  a client for a TI endpoint gets a `tls.Config` whose `VerifyConnection` applies the
  shared verification rules (natively under `spec/pki-validation`, or through `ti`),
  never the system roots alone (TASK-98).

## 3. Keys and cryptography

Cryptography comes from the standard library (`crypto/...`, `crypto/tls`,
`crypto/mlkem`, `crypto/hkdf`). `brainpool` is the one exception, because the standard
library has no brainpool curves: its field arithmetic is generated by Fiat Cryptography
and formally verified there, wrapped in the shape of the standard library's `nistec`; it
is frozen (bugfix and security only), and new brainpool work happens in Rust.

| [Key rule](../../docs/design/keys.md) | Go |
|---|---|
| sign | `crypto.Signer`, honouring `SignerOpts` (a digest with its hash, or `crypto.Hash(0)` for the whole message as `ed25519` uses it) |
| decrypt, key agreement | `crypto.Decrypter`; a key-agreement interface over `crypto/ecdh` |
| async and cancellable, capabilities, attestation | a small interface of our own next to `crypto.Signer` with a `context.Context` (to add, TASK-87) |
| software key | `*ecdsa.PrivateKey`, `ed25519.PrivateKey`, … created at the edge (`cmd/`) only |
| zeroized key bytes | byte slices overwritten after use, never kept as `string` |
| TLS | `crypto/tls` with its defaults; the certificate key `tls.Certificate.PrivateKey` is a `crypto.Signer`, so it can be HSM-backed |

JWKs are a wire format for public keys and for import and export, not how a private key
is held. `epa` follows the key rules to the end: the SMC-B identity, its signatures and
the IDP-Dienst flow run in the Rust `ti`, and the private key never enters the Go
process. Randomness from `crypto/rand` only (`rand.Read`, `rand.Text` for identifiers,
state, nonces and codes).

## 4. Errors and result codes

Errors are values wrapped with `%w`; sentinel errors (`ErrLimitExceeded`, …) map to the
result codes of a shared specification, as the spec's table lists (`spec/pkcs12`:
`limit_exceeded` is `ErrLimitExceeded`).

## 5. Testing

- Standard `testing` only: table-driven tests, subtests, `t.Helper`, `t.Cleanup`,
  `t.Context`. No assertion frameworks; a test states what it expected and what it got.
- Fakes over mocks; `net/http/httptest` for handlers and clients, `testing/synctest` for
  code that waits or times out, golden files under `testdata/` for wire formats.
- Requirement-named tests: `func TestP12_036…`, or the subtest name
  `t.Run("P12-036 …")`; the implementing code cites the requirement in a comment.
- Gated tests skip loudly without their variable:
  `t.Skipf("set ZERO_PDP_E2E_URL to run: <what this proves>")`; the suites are in
  [development.md](./development.md#gated-tests).

## 6. Verification and tooling

| Category | Go tool | When | Today |
|---|---|---|---|
| lints, API misuse | `go vet`, staticcheck | check | `just lint` |
| security smells, error handling | golangci-lint (gosec, errorlint, gocritic, revive, …) | check | `just golangci`, not in `just check` |
| race detection | `go test -race ./...` | check | not in `just check` |
| fuzzing | `go test -fuzz` (below) | release, design time | `brainpool`, `pkcs12` |
| supply chain | govulncheck; `go mod tidy`, `go mod verify` | check | `just vuln`, `just tidy` |
| business API contracts | gematik OpenAPI ruleset with Spectral | check | `just api-lint` (skips without the internal ruleset) |
| current idioms | modernize | check | `just check` |
| corpora, interop | spec corpora, interop runs with Rust | check | partial |

Formal verification in the Rust sense (Kani, hax) has no maintained Go equivalent; Go
keeps security-critical algorithms out of hand-written code instead (standard library,
generated and verified Fiat code, or the Rust core), and covers the rest with fuzzing,
the race detector and the shared spec corpora.

## 7. Fuzzing

Native fuzz tests, `func FuzzXxx(f *testing.F)`, next to the code they cover, seeded with
`f.Add` from the spec corpora and real artefacts; crashers land in
`testdata/fuzz/FuzzXxx/` and are committed, which makes each one a regression test.
A `just fuzz` recipe that runs every target for a short time and fails on a crash comes
with the first server-side targets (TASK-90). Targets needed:
DPoP proofs, client assertions, PAR and token requests, entity statements and trust
chains (`oidf`), ID tokens and JWKS (`oauth`), nonces, VAU messages and CBOR (`epa`),
routes and policy files (`pep`).

## 8. Dependencies

- Library modules aim for zero third-party requirements; `golang.org/x` is acceptable,
  test-only modules are not (use `testing`).
- A command may add what the standard library cannot do (a Postgres driver, a Caddy
  plugin host), with the reason recorded next to the requirement.
- Duplicates are removed: one YAML library, one JOSE library, one way to make IDs.
- `go.mod` follows the latest Go release and the latest release of every requirement;
  no `replace` directives on `main`. Weigh the tree with `go mod graph`.

## 9. Crossing languages

Go never links Rust: no cgo, every binary builds with `CGO_ENABLED=0` (static,
cross-compiled, without a C toolchain). Go uses the Rust core across a process boundary
(`ti` subprocesses today, a typed client for `ti serve` later) or implements a function
natively under a shared specification, as [interop](../../docs/interop.md) describes.
The Go client of a process boundary pools connections and buffers (`sync.Pool`), sits
behind a consumer interface, and checks the peer's version at start-up.

## 10. Servers

The [server rules](../../docs/design/servers.md), in Go terms:

- A server package exports an `http.Handler` (or a constructor returning one) and a
  `Config` struct.
- The service is a package with typed methods (`Authorize(ctx, AuthorizeRequest)
  (AuthorizeResponse, error)`); `http.Handler`s decode, call it and encode. The same
  service can sit behind another adapter (RPC, socket) without change.
- Served by `net/http` with explicit timeouts (`ReadHeaderTimeout`, `ReadTimeout`,
  `WriteTimeout`, `IdleTimeout`; proxies without whole-request deadlines), body limits
  (`http.MaxBytesReader`) and graceful shutdown on SIGTERM. Routing uses `http.ServeMux`
  with method and path patterns; middleware is `func(http.Handler) http.Handler`.
- Request decoding is strict: `json.Decoder` with `DisallowUnknownFields`, explicit
  `Validate()` methods, and URL, header and form values parsed into types before use.
- Shared state goes through `kv.Store`; the in-memory store is for tests and single-node
  development only, and production configuration rejects it. The security state uses the
  transactional backend (Postgres): `Take` for single-use values, transactions for
  read-modify-write; `kv` encrypts records in the workload before they reach the store.
- Nonces, `state`, CSRF tokens and similar short-lived values are sealed (AEAD with a
  shared workload key, issue time and purpose in the associated data) and verified
  without a lookup; access tokens are signed JWTs (RFC 9068), sender-constrained with
  DPoP, validated offline by the PEP.
- Outbound HTTP goes through one constructor that applies the SSRF policy (allowed
  hosts, no private or link-local addresses after DNS resolution, no cross-host
  redirects, timeouts, response size limits).
- Caches use one shared pattern (keyed by input hash, configuration and trust-material
  version; bounded TTL; invalidated on trust-material reload; single-flight against
  stampedes), the same rules as `ti-store` on the Rust side.
- Telemetry through one internal instrumentation interface with an OpenTelemetry or
  Prometheus exporter chosen in `cmd/`, and `slog` JSON to stdout; cloud services (KMS,
  attestation, managed databases) behind interfaces with an adapter per provider.
- Images are `scratch` with a static `CGO_ENABLED=0 -trimpath` binary, `USER 65532`,
  base images pinned by digest, signed with provenance and an SBOM. Test-only code sits
  behind build tags and is not in production builds.
