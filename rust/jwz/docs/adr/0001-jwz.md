# ADR 0001: jwz, a JOSE library for Rust

Status: accepted (milestone 1 in progress), 2026-10-09. Amended 2026-11-06 (TASK-225): the
crate jwz-brainpool became the module `ti_jwz::brainpool`, behind ti-jwz's `legacy`
feature, since brainpool is TI-only; below, its old name stands for that module. Amended
2026-11-08 (TASK-271, jwz 0.2): profiles are explicit lists built from constants, and
they bind signing, encryption and key curves; see "Decisions taken for jwz 0.2", which
replaces the S3 decision on composition and the S5 decision on ePA's keys.
Amended 2026-11-08 (review of jwz): the alternatives were checked again against their
current releases; see "Alternatives reconsidered".

## Context

New TI components (TI 2.0, ZETA, PoPP, OpenID Federation) need JOSE in Rust, and so do
existing interfaces that still speak brainpool (IDP, ePA and E-Rezept VAU handshakes,
SMC-B and HBA keys). The candidates fall short:

- `jose-rs` 0.9 has closed algorithm and curve enums (`BP256R1` cannot be added from
  outside), no JWE ECDH-ES, the older RustCrypto line (p256 0.13, ecdsa 0.16, rsa 0.9),
  FFI by default (`cryptoki`) and probably no wasm32 build. It stays useful as an
  interop oracle.
- RustCrypto's `jose-*` crates stalled at 0.1.2.
- In this repository's Go code, brainpool JOSE lives in its own package
  (`go/brainpool/josebp`), outside the general JOSE library.

### Alternatives reconsidered (2026-11-08)

A review asked whether the TI crates could use an established JOSE crate instead. Their
releases on crates.io as of 2026-11-08:

| Crate | Release | Crypto | JWE | TI brainpool | Keys as functions | Browser wasm32 |
| --- | --- | --- | --- | --- | --- | --- |
| `jsonwebtoken` | 11.1.0, 2026-09 | aws-lc-rs, or pure Rust with `rust_crypto`, or an own `CryptoProvider` | no | no: a closed set of algorithms | no: keys as bytes, synchronous providers | not stated |
| `jwt-simple` | 0.15.0, 2026-09 | BoringSSL, or pure Rust with `pure-rust` | yes (RSA-OAEP, AES-KW, ECDH-ES) | no | no | WASI only (`wasm32-wasip1`) |
| `josekit` | 0.10.3, 2025-05 | OpenSSL (C) | yes | no | no | no |
| `biscuit` | 0.8.0, 2026-04 | ring (C and assembly) | partly | no | no | no |
| `compact_jwt` | 0.6.0, 2026-08 | `crypto-glue`, HSM support | partly | no | partly (HSM) | not stated |

Pure-Rust crypto is no longer unique to jwz: `jsonwebtoken` and `jwt-simple` offer it as an
option. What none of them offers is the combination the TI needs, and that decides:

- **The TI's brainpool algorithms**: `BP256R1` (IDP-Dienst), `ES256` on a brainpoolP256r1
  key (ePA) and `ECDH-ES` on BP-256 (encryption to the IDP). Closed algorithm sets cannot
  take them from outside; jwz's open registry does, in ti-jwz.
- **JWS and JWE in one crate**, both in pure Rust, under one policy.
- **Keys as functions**, synchronous and asynchronous: the SMC-B or HBA signs through the
  Konnektor, an HSM or WebCrypto signs where the key lives.
- **No C and no `unsafe`** as the only build, not an option: `#![forbid(unsafe_code)]`, and
  the dependency tree held to an approved list (`just unsafe-free`); and with it
  `wasm32-unknown-unknown`, the browser, as a first-class target.
- **Profiles that bind what is produced** as well as what is accepted (TASK-271, TASK-276).

Whether the other crates forbid `unsafe` in their own code was not checked. They remain
useful as interop oracles in jwz's tests, as `jose-rs` and Python's `jwcrypto` are.

So jwz is a general JOSE library, with an open registry and pluggable keys and
backends, and profiles as a policy layer
on top. The TI profile (`ti-jwz`) is the first consumer and test bed, not the design
centre.

## Key points

Each key point has a check that fails when it is broken.

1. **Pluggable crypto through traits.** Every primitive (ECDSA, ECDH, EdDSA, AES-GCM,
   AES-KW, HMAC, hashing, RNG) is reached through `jwz::crypto`. The pure-Rust backend
   is the feature `crypto-rustcrypto`; other backends (`jwz-webcrypto`, `jwz-aws-lc`) are
   crates of their own implementing the same traits. The core compiles without any
   backend. Checks: `cargo hack --each-feature` (no backend is a valid build),
   `just jwz-backends` (no openssl, ring, aws-lc or cryptoki in jwz's tree), a
   `compile_error!` guard per in-crate backend once a second one exists.
2. **WASM is a first-class target.** Every jwz crate checks on `wasm32-unknown-unknown`;
   no `SystemTime`, no threads; randomness only through the backend's `Rng`. Checks:
   `just wasm32`; browser round trips with `wasm-bindgen-test` (design time, see below).
3. **Validation profiles.** A `Profile` bundles a `Policy` (algorithms, the curves of
   signing keys and of ECDH-ES keys, headers, `kid`, sizes) and a `ClaimsPolicy`. A
   profile is the explicit lists its construction results in: constants composed with
   `Profile::with(&Algorithms)`. The policy binds what jwz accepts and what it produces:
   parsing, verification, signing and encryption all refuse an algorithm or a key curve
   it does not list, and a header it would refuse. jwz ships `strict` (default) and `rfc7518-interop`, ti-jwz `ti` and
   `ti-legacy`; `oauth-dpop`, `openid-federation`, `eudi-wallet` are reserved.
4. **HSM and opaque keys.** Private keys are trait objects; nothing needs key bytes
   except software keys. Signers and key agreement have sync and async forms. Proven in
   milestone 1 by `MockHsmSigner` (a handle only) and `TestKmsSigner` (async, over a
   channel); `jwz-pkcs11` (milestone 2) must need no change to the core.

## Principles

1. **Open algorithm registry.** Algorithms, curves and key types are interned names
   (`jwa::Name<K>`) with metadata in a `jwa::Registry`; RFC 7518 and RFC 8037 are
   pre-registered, extension crates register more (`ti_jwz::brainpool::register`).
2. **Pluggable keys.** `Signer`, `Verifier`, `KeyAgreement`, `KeyWrap`, `ContentCipher`
   traits; HSMs, smartcards, WebCrypto and remote signers implement them.
3. **Policy is an input to every parse.** The default is strict and modern; permissive is
   an explicit choice.
4. **Type-state for trust.** `Jws<Unverified>` has no payload accessor; `Jwe<Encrypted>`
   has no plaintext accessor.
5. **Parsing safety as invariants.** Token size cap, strict base64url, duplicate JSON
   members rejected, `crit` enforced, `none` unrepresentable, the header never selects
   the algorithm.
6. **Sans-I/O core.** `jku`/`x5u` fetching is a `Fetcher` trait; jwz does no network.
7. **`no_std` + `alloc`** for jwz; `std` only where needed; wasm32 for every crate.
8. **Pure Rust by default** on the RustCrypto 0.14 line; openssl, ring and aws-lc only
   ever in a backend crate of their own.

## Decisions taken while starting milestone 1

- **The registry is a value, not a global.** jwz passes a `Registry` (with the `Policy`) to every parse. Registration still happens
  at run time from any crate, but there is no hidden mutable state, two parts of a
  program can know different algorithms, and `no_std` needs no lock.
- **`none` cannot be named.** No constant exists; the registry refuses to register or
  look up `none` in any casing (RFC 7518 §3.6).
- **The Concat KDF is jwz code, not a backend primitive.** It runs over the backend's
  `Hash` and is the same for every backend, so the one verified implementation (hax,
  below) is the one in use. The spec's `Kdf` trait is therefore `Hash`.
- **Signer and Verifier build on RustCrypto's `signature` 3.0 traits.** Its async traits
  use `async fn` and cannot be trait objects, so jwz adds thin `dyn`-compatible wrappers
  over them (stage S2); a later move into RustCrypto stays a rename.
- **Async futures are boxed and not `Send`**, so they run in a browser; a server that
  needs `Send` wraps its backend at its own layer. Async accessors end in `_async`.
- **Brainpool is brainpoolP256r1 only**: `BP256R1` and `BP-256`, in `ti_jwz::brainpool`.
  BP384/BP512 are not registered (no BP512 crate exists; no TI interface needs them).
- **RSA is a data model only in milestone 1.** The names are registered as reserved, the
  `rsa` feature refuses to build (`just jwz-rsa-guard`).
- **Post-quantum names are reserved**: ML-DSA-44/65/87, ML-KEM-512/768/1024.
- **Layout: flat in the zero-lab `rust/` workspace** (`rust/jwz`,
  `rust/ti-jwz`), sharing its lock file, supply chain, deny configuration and Justfile.
  Tags follow the workspace convention `rust/<crate>/vX.Y.Z`. Because the shared
  `deny.toml` also governs `ti-cli`, whose TLS uses rustls with ring, backend purity is
  a tree check (`just jwz-backends`) rather than a deny ban. Moving jwz to a repository
  of its own later means moving two directories and adapting tags and tooling there.
- **Licence: EUPL-1.2, gematik GmbH**, as for every crate in the workspace. The crate
  names `jwz` and `ti-jwz` are confirmed (maintainer, 2026-11-06, TASK-22); both stay
  `publish = false` until the registry decision is made.
- **Design time and build time are separate.** Building and `just check` need stable
  Rust only. Formal verification (Kani, hax/F*), interop fixture generation, fuzzing and
  browser round trips run at design time and commit their results with a stamp (the
  hash of their inputs and the tool versions); `just check` fails on a stale stamp, and
  `just jwz-recheck` re-runs only what changed (stage S7/S8).

## Decisions taken in stage S2 (backend, JWK, keys)

- **A key is bound to one algorithm.** `SoftwareKey::from_jwk(jwk, alg, …)` refuses a
  key whose type or curve does not fit `alg`, whose own `alg` member names another one
  (RFC 7517 §4.4), or whose private part does not belong to its public part. A token
  header can therefore never pick another algorithm for a key.
- **`Signer`/`Verifier` are RustCrypto's.** Any `signature::Signer<jwz::keys::Signature>`
  that is a `JwsKey` is a jwz `Signer`; every `Signer` is an `AsyncSigner`. A key that
  only answers asynchronously (an HSM, a KMS) implements `AsyncSigner` directly; it
  cannot also be a synchronous signer, which is what such keys are.
- **Duplicate JSON members are rejected everywhere**, not only in headers (RFC 7515
  §5.2 step 4 allows either; serde_json keeps the last one silently).
- **Errors never carry input.** `Error` is a code plus a static context; jwz errors
  survive the trip through `signature::Error` as its source.
- **The RustCrypto backend is `Send + Sync`** (its random source must be), so a server
  shares one backend. Ed25519 uses strict verification (canonical encodings, no
  small-order keys); ECDSA signing is deterministic (RFC 6979).
- **AES Key Wrap enforces RFC 3394's minimum** of two 64-bit blocks, which `aes-kw`
  does not (found by Wycheproof).
- **Browser randomness** comes from `getrandom`'s `wasm_js` backend, enabled only for
  `wasm32-unknown-unknown`, against getrandom's advice for libraries; a non-browser
  wasm host passes its own source to `RustCrypto::with_rng`.
- **serde_json is a direct dependency** of jwz, not the workspace entry, so jwz stays
  `no_std` while other crates use serde_json with `std`.
- Dependencies and their audit status: `docs/dependencies.md`.

## Decisions taken in stage S3 (JWS, profiles)

- **One acceptance site.** `Policy::check_jws` decides on `alg`, `crit`, key-reference
  parameters, `typ` and `b64`; `Jws::parse` calls it before any cryptography, and
  `Jws::verify` is the only place a JWS signature is checked.
- **Headers live in their own module** (`jwz::header`), shared by JWS and JWE, so
  `profile` judges headers without depending on `jws` (module rules of the spec).
- **`crit` (RFC 7515 §4.1.11)**: a non-empty array of distinct extension names, each
  present in the header, none a registered parameter, each listed in the policy's
  `understood_critical`.
- **Key references are opt-in** (`jwk`, `jku`, `x5u`, `x5c`): a token that brings its
  own key proves nothing until the application validates that key, so the strict
  profile refuses them and `KeyReferences` turns each on.
- **RFC 7797 (`b64`) is refused**: it changes what is signed and is not implemented.
- **JSON serialization is stricter than RFC 7515**: `alg` and `crit` must be in the
  protected header, every signature entry needs one, and protected and unprotected
  headers must be disjoint (RFC 7515 §7.2.1).
- **Composition only widens** (`Profile::with`): it appends lists, so whatever one
  profile accepts, every profile built from it accepts (the property Kani checks). A
  narrower profile is written, not composed. Since jwz 0.2 `with` takes an `Algorithms`
  bundle, not another profile (see "Decisions taken for jwz 0.2").
- **Reserved profile names** (`oauth-dpop`, `openid-federation`, `eudi-wallet`) fail by
  name instead of handing out another profile.
- **x5c**: jwz decodes the chain (standard base64, RFC 7515 §4.1.6) and checks
  `x5t#S256` against the leaf; validating the chain is a `ChainValidator`'s job.

## Decisions taken in stage S4 (JWE, Concat KDF, JWT)

- **`Policy::check_jwe` is JWE's acceptance site**, sharing `crit`, key references and
  `typ` with JWS. It refuses what jwz does not implement by key management mode and
  content cipher kind, not by name: RSA, PBES2 and CBC-HMAC are known and refused as
  unsupported, so a later implementation only flips a registry entry.
- **`zip` is refused** (RFC 7516 §4.1.3): compressing before encrypting leaks the
  plaintext's redundancy, and decompressing turns a small token into a large allocation.
- **Structure before cryptography**: IV and tag lengths come from the registry and are
  checked at parse; the direct modes (`dir`, `ECDH-ES`) need an empty encrypted key and
  the wrapping modes a non-empty one (RFC 7516 §5.2 step 10); `epk` must be a public EC
  key on a registered, available curve, and `apu`/`apv` base64url; all of this at parse,
  so a malformed token never reaches a key.
- **The Concat KDF works on Z as bytes** over the backend's `Hash`
  (`jwe::ecdh::concat_kdf`), not over `elliptic_curve::Curve` as the plan said: Z is the
  same kind of value on every curve, so one function serves P-256, BP-256 and whatever a
  backend adds, without making jwz generic over RustCrypto's curve types (which an HSM or
  WebCrypto backend could not provide). It is straight-line code over a hash, the form
  hax extracts in S7.
- **ECDH-ES has one site** (`jwe::ecdh`): the sender's ephemeral key and the KDF; the
  recipient's Z comes from a `KeyAgreement`, so the private key can live in an HSM. The
  `epk` curve must equal the recipient key's curve.
- **Further curves come through `crypto::Extended`**: a backend plus ECDSA and ECDH
  providers for other curves, answering from those first. `jwz-brainpool` (S5) uses it,
  so brainpool never becomes a second backend and everything else (random source, hash,
  AEAD, key wrap) stays the base's.
- **JSON serialization is stricter than RFC 7516**: `enc`, `crit` and `zip` must be in the
  protected header, so the content cipher is covered by the tag (RFC 7520 §5.12, which
  protects nothing, is refused); `alg` may be per recipient, as several recipients need
  different ones, and a changed `alg` gives a different CEK. The direct modes refuse
  several recipients.
- **Symmetric keys follow their JWK `alg`**; for `dir` the `enc` is accepted too, as
  RFC 7520 §5.6 publishes such keys.
- **JWT claims are checked on a payload, not a token** (`jwt::Claims`): the JWS and JWE
  type-states already make the payload available only after verification or decryption.
  `ClaimsPolicy` is part of `Profile`; time comes from a `Clock` (`SystemClock` with
  `std` except in the browser, where std has no clock and the caller brings one over
  `Date.now()`; `FixedClock` for tests). NumericDate fractions are rounded down, negative values
  refused; `strict` requires `exp` and allows 60 seconds of skew.

## Decisions taken in stage S5 (brainpool, TI profiles)

- **The `epk` curve is policy** (`Policy::key_agreement_curves`), checked in
  `check_jwe`: which curves a program's registry knows must not decide which curves a
  profile accepts, so `ti()` refuses a `BP-256` `epk` even with the brainpool registry.
- **jwz-brainpool is names plus primitives**: `Bp256` implements `Ecdsa` and `Ecdh` on
  RustCrypto's `bp256`, and `backend()` adds them through `crypto::Extended`. JWS, JWE,
  the KDF, keys and policies stay jwz's code, the same for every curve.
- **ePA's `ES256` on brainpool keys is a key, not an algorithm.** RFC 7518 §3.4 makes
  ES256 P-256, and jwz's registry keeps that. `ti_jwz::brainpool::BrainpoolEs256Key` is
  bound to `ES256` and verifies on brainpoolP256r1; the verifier chooses it (from the
  `x5c` certificate's key), so the header never chooses the curve, and only programs
  that enable ti-jwz's `legacy` can do it at all. Since jwz 0.2 `ti()` accepts these
  tokens because it lists `BP-256` among its signing curves, not merely because their
  algorithm is ES256; `strict()` refuses them.
- **Brainpool JWE is encryption only** in milestone 1: jwz encrypts to a `BP-256` key
  (what TI clients do towards the IDP), and no profile accepts an `epk` on `BP-256`, so
  decryption is neither tested nor offered. Decryption is a backlog task.
- **Sources**: `BP256R1`/`BP-256` are defined by gemSpec_IDP_Dienst V2.2.0, not
  gemSpec_Krypt; the TI profiles cite both, rule by rule, in `ti-jwz`'s documentation.

## Decisions taken in stage S6 (interop, fuzzing)

- **Interop is brainpool only, in `ti-jwz`**: the RFC vectors already pin the
  standard algorithms, and brainpool is where gematik's names and implementations need
  agreement. The oracles are `go/brainpool/josebp` (what the Go IDP and ePA clients use)
  and Python jwcrypto, independent of each other and of jwz.
- **Design time makes fixtures, build time checks them.** `just jwz-interop` needs Go and
  Python; `cargo test` needs neither. jwz's tokens are deterministic (fixed random
  source, RFC 6979), so the test regenerates them and fails when jwz's output changed
  since the oracles last checked it, the same idea as the S7 stamps.
- **Each oracle's gaps are recorded, not hidden**: josebp reads compact JWS only and does
  not decrypt; jwcrypto binds ES256 to P-256. Every jwz token must be accepted by at least
  one oracle, and no oracle may refuse one.
- **Fuzzing lives outside the workspace** (`jwz/fuzz`, its own lock file): libfuzzer
  needs nightly and must not reach the workspace's dependency checks. Targets cover every
  parser and the decryption and verification paths behind them; the JWK target also
  checks that a parsed key survives its own serialization.

## Decisions taken in stage S7 (verification, traceability)

- **The proven code is a small core, the checks stay around it.** `jwe::ecdh::kdf`
  (`be32`, `other_info`, `rounds`) is written in the subset hax extracts: no trait
  objects, no zeroizing wrappers, the hash as a trait. `concat_kdf` keeps the length
  checks, the zeroization and the truncation, and is covered by an exhaustive unit test
  of the layout and the RFC vector.
- **The specification is written from the documents, not from the code**
  (`verification/hax/Jwz.Kdf.Spec.fst`), and the Rust functions carry `ensures` clauses
  that refer to it, so the claim sits next to the code a reviewer reads.
- **`hax-lib` is a `cfg(hax)` dependency**: annotations behind `cfg_attr(hax, …)`, never
  compiled in a build. Its crates are in `Cargo.lock` and exempted in `cargo vet`; the
  alternative, typechecking the extraction without preconditions, would leave panic
  freedom unproven.
- **The proof found a real gap**: lengths that each fit 32 bits can sum past `usize` on a
  32-bit target (wasm32). `concat_kdf` now refuses that case.
- **Kani where CBMC copes**: the base64url round trip is proven per length; canonicity of
  base64ct's decoder over symbolic strings runs out of memory and stays with tests and
  fuzzing. Nothing that parses JSON is model-checked.
- **Design time and build time are separate.** Proofs, extraction and interop need their
  tools; their results are stamped with the SHA-256 of their inputs, and `just check`
  (stable Rust, no proof tools) fails on a stale stamp. `just jwz-recheck` reruns only
  what changed.
- **Traceability is generated by a test** (`tests/traceability.rs`): the table of
  specification references, their source locations and the tests named after them is
  rebuilt on every `cargo test` and must match `docs/traceability.md`.

## Decisions taken for jwz 0.2 (fully specified algorithms, TASK-241)

- **`Ed25519` per RFC 9864.** The registry has `Ed25519` (available) and `Ed448`
  (reserved, as P-384 and P-521 are: rarely used, and its backend would be a new
  dependency). A fully specified algorithm names its curve, so a key for it must be on
  that curve, and a JWK whose `alg` says `Ed25519` is not a key for `EdDSA`, nor the
  reverse (RFC 9864 §5, §7: one key, one algorithm).
- **`strict` lists `Ed25519`, not `EdDSA`.** RFC 9864 deprecates the polymorphic name.
  Since a profile's lists bind signing as well as verification, keeping `EdDSA` in
  `strict` for verification only would need a second list; instead it leaves `strict`
  and stays a constant (`EDDSA`) for a profile that must talk to an older peer, and in
  `rfc7518-interop`. The TI profiles have neither: gemSpec_Krypt admits no EdDSA.

## Decisions taken for jwz 0.2 (profiles bound, TASK-271)

- **A profile is explicit lists, the result of its construction.** Building blocks are
  constants of `Algorithms` (slices of signature, key-encryption and content-encryption
  algorithms, signing curves, key-agreement curves): jwz has `ECDSA_NIST`, `ED25519`, `EDDSA`,
  `HMAC`, `ECDH_ES_P256`, `ECDH_ES_DIRECT_P256`, `AES_KW`, `DIRECT`, `AES_GCM`,
  `AES_128_GCM` and `AES_256_GCM`, each one RFC construction; ti-jwz has
  `EPA_BRAINPOOL_KEYS`, `BRAINPOOL_SIGNATURES` and `BRAINPOOL_KEY_AGREEMENT`.
  `Profile::new(name, version)` starts with none and strict defaults for everything
  else; `Profile::with(&Algorithms)` appends without duplicates and changes nothing but
  the lists. There are no families and no removal (`only`, `without`): what a profile
  accepts is read off its construction, `Profile::new("ti", 2).with(&ECDSA_NIST)
  .with(&EPA_BRAINPOOL_KEYS)…`. `rfc7518-interop` is the one exception: its lists are
  what the registry has available, so it follows what a program registers.
- **The union of profiles is gone.** `Profile::with(&Profile)`, `Policy::with` and
  `ClaimsPolicy::with` mixed lists with settings (`typ`, `kid`, claims) whose union has
  no obvious meaning; composition is of algorithm lists only, settings are fields.
- **Signing-key curves are a list of their own** (`Policy::signing_curves`), as the
  `epk` curves are for JWE. A key states its curve (`JwsKey::curve`, default none:
  `SoftwareKey`, ti-jwz's `BrainpoolEs256Key` and the test doubles state theirs); its
  effective curve is that, or else its algorithm's registered curve (P-256 for ES256).
  For an algorithm whose key type has curves (`EC`, `OKP`) the effective curve must be
  listed, and a key with none (an EdDSA signer that does not say) is refused. HMAC is
  bound by its algorithm alone.
- **Verification is bound without changing its signatures.** Parsing records the rule
  (the policy's signing curves, the algorithm's key type and registered curve), and
  `verify`, `verify_async`, `verify_with` and `verify_with_async` apply it: a key on a
  curve the profile does not list is refused with `PolicyViolation`, and a resolved one
  is passed over like any key that does not fit. `PolicyViolation`, not `KeyMismatch`:
  the key fits its algorithm; it is the profile that does not allow it.
- **Production is bound.** `jws::sign`, `jws::sign_async` and `jws::json::sign` take the
  policy and the registry and refuse an algorithm or a signing curve the policy does
  not list; `jwe::encrypt` and `jwe::json::encrypt` take the policy and refuse an `alg`,
  an `enc` or an ECDH-ES recipient curve it does not list (`PolicyViolation`, before any
  key is used). jwz no longer produces what its own profile refuses (RFC 8725 §3.1).
- **The produced header is bound too** (TASK-276, RFC 8725 §3.11). Before signing, and
  before key agreement for encryption, the header jwz writes runs the checks a received
  one gets (`typ`, a required `kid`, key references, `crit`, `b64`, and `zip` for JWE),
  in the JSON serializations each signature's or recipient's visible header. A profile
  with a `typ` therefore neither signs nor accepts a token without it. jwz does not add
  the `typ` itself: the caller sets it, and the profile checks it, as for every other
  parameter.
  `Policy::check_signing_key` and `Policy::check_encryption` are the acceptance sites;
  `check_jwe` uses the latter for received headers, so both directions share one check.
  Encryption takes RFC 7516's own split (§7.2.1): a `jwe::Recipient` (its `alg`, key and
  header parameters) and, for the JSON serialization, `jwe::json::Shared` (`enc`, the
  protected header parameters, `aad`), so the producers stay within clippy's limit on
  parameters without allowing the lint.
- **One list per direction is one list.** `key_agreement_curves` serves both the `epk`
  of a received JWE and the recipient key of a produced one. TI clients encrypt to the
  IDP's `BP-256` key but decrypting brainpool JWE is not offered, so no shipped profile
  lists `BP-256` for key agreement; the IDP client adds `BRAINPOOL_KEY_AGREEMENT` to
  `ti_legacy()` for that one request.
- **The ePA exception is stated in ti-jwz.** `ti()` lists `BP-256` among its signing
  curves (`EPA_BRAINPOOL_KEYS`, gemSpec_Krypt Tab_KRYPT_002a), so ES256 with a
  brainpoolP256r1 key passes `ti()` and fails `strict()`; `ti_legacy()` is `ti()` with
  `BRAINPOOL_SIGNATURES`. The profile versions went to 2 (`strict`, `rfc7518-interop`,
  `ti`, `ti-legacy`): each now refuses keys on curves it does not list.

## Auditability

Written for reviewers who are not Rust specialists: one security decision in one place
(algorithm acceptance only in `profile::Policy::check`, signature verification only in
`jws::verify`, key agreement only in `jwe::ecdh`); short straight-line functions; no
macro-generated logic beyond `compile_error!` and derives; explicit type-state instead
of "already checked" flags; every rule carries its source (`// RFC 7515 §5.2 step 8`,
`// gemSpec_Krypt V2.50.0 …`) and the test covering it names the same source; no panics
on input (`unwrap`, `expect`, `panic`, indexing denied outside tests); constant-time
comparison of MACs, tags and thumbprints; secrets in `Zeroizing`; every dependency
justified in `docs/dependencies.md`; randomness only through `Rng`, so every path is
reproducible in tests.
