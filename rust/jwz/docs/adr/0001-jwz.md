# ADR 0001: jwz, a jwx-like JOSE library for Rust

Status: accepted (milestone 1 in progress), 2026-10-09.

## Context

New TI components (TI 2.0, ZETA, PoPP, OpenID Federation) need JOSE in Rust, and so do
existing interfaces that still speak brainpool (IDP, ePA and E-Rezept VAU handshakes,
SMC-B and HBA keys). The candidates fall short:

- `jose-rs` 0.9 has closed algorithm and curve enums (`BP256R1` cannot be added from
  outside), no JWE ECDH-ES, the older RustCrypto line (p256 0.13, ecdsa 0.16, rsa 0.9),
  FFI by default (`cryptoki`) and probably no wasm32 build. It stays useful as an
  interop oracle.
- RustCrypto's `jose-*` crates stalled at 0.1.2.
- Go's `jwx` shows the shape we want: an open registry, pluggable keys, a library that
  is complete over time. Even there, brainpool lives outside it: `go/brainpool/josebp`
  implements it, `go/gemidp/jwx.go` only registers the name.

So jwz is a general JOSE library in the spirit of `jwx`, with profiles as a policy layer
on top. The TI profile (`ti-jwz`) is the first consumer and test bed, not the design
centre.

## Key points

Each key point has a check that fails when it is broken.

1. **Pluggable crypto through traits.** Every primitive (ECDSA, ECDH, EdDSA, AES-GCM,
   AES-KW, HMAC, hashing, RNG) is reached through `jwz::crypto`. The pure-Rust backend
   is the feature `crypto-rustcrypto`; other backends (`jwz-webcrypto`, `jwz-aws-lc`) are
   crates of their own implementing the same traits. The core compiles without any
   backend. Checks: `cargo hack --each-feature` (no backend is a valid build),
   `just jwz-backends` (no openssl, ring, aws-lc or cryptoki in jwz's tree), a
   `compile_error!` guard per in-crate backend once a second one exists.
2. **WASM is a first-class target.** Every jwz crate checks on `wasm32-unknown-unknown`;
   no `SystemTime`, no threads; randomness only through the backend's `Rng`. Checks:
   `just wasm32`; browser round trips with `wasm-bindgen-test` (design time, see below).
3. **Validation profiles.** A `Profile` bundles a `Policy` (algorithms, headers, sizes),
   a `ClaimsPolicy` and key constraints; profiles are data and composable. Milestone 1
   ships `strict` (default), `rfc7518-interop`, `ti` and `ti-legacy`, and reserves
   `oauth-dpop`, `openid-federation`, `eudi-wallet`.
4. **HSM and opaque keys.** Private keys are trait objects; nothing needs key bytes
   except software keys. Signers and key agreement have sync and async forms. Proven in
   milestone 1 by `MockHsmSigner` (a handle only) and `TestKmsSigner` (async, over a
   channel); `jwz-pkcs11` (milestone 2) must need no change to the core.

## Principles

1. **Open algorithm registry.** Algorithms, curves and key types are interned names
   (`jwa::Name<K>`) with metadata in a `jwa::Registry`; RFC 7518 and RFC 8037 are
   pre-registered, extension crates register more (`jwz_brainpool::register`).
2. **Pluggable keys.** `Signer`, `Verifier`, `KeyAgreement`, `KeyWrap`, `ContentCipher`
   traits; HSMs, smartcards, WebCrypto and remote signers implement them.
3. **Policy is an input to every parse.** The default is strict and modern; permissive is
   an explicit choice.
4. **Type-state for trust.** `Jws<Unverified>` has no payload accessor; `Jwe<Encrypted>`
   has no plaintext accessor.
5. **Parsing safety as invariants.** Token size cap, strict base64url, duplicate JSON
   members rejected, `crit` enforced, `none` unrepresentable, the header never selects
   the algorithm.
6. **Sans-I/O core.** `jku`/`x5u` fetching is a `Fetcher` trait; jwz does no network.
7. **`no_std` + `alloc`** for jwz; `std` only where needed; wasm32 for every crate.
8. **Pure Rust by default** on the RustCrypto 0.14 line; openssl, ring and aws-lc only
   ever in a backend crate of their own.

## Decisions taken while starting milestone 1

- **The registry is a value, not a global.** jwx registers into package-level state;
  jwz passes a `Registry` (with the `Policy`) to every parse. Registration still happens
  at run time from any crate, but there is no hidden mutable state, two parts of a
  program can know different algorithms, and `no_std` needs no lock.
- **`none` cannot be named.** No constant exists; the registry refuses to register or
  look up `none` in any casing (RFC 7518 §3.6).
- **The Concat KDF is jwz code, not a backend primitive.** It runs over the backend's
  `Hash` and is the same for every backend, so the one verified implementation (hax,
  below) is the one in use. The spec's `Kdf` trait is therefore `Hash`.
- **Signer and Verifier build on RustCrypto's `signature` 3.0 traits.** Its async traits
  use `async fn` and cannot be trait objects, so jwz adds thin `dyn`-compatible wrappers
  over them (stage S2); a later move into RustCrypto stays a rename.
- **Async futures are boxed and not `Send`**, so they run in a browser; a server that
  needs `Send` wraps its backend at its own layer. Async accessors end in `_async`.
- **Brainpool is brainpoolP256r1 only**: `BP256R1` and `BP-256`, in `jwz-brainpool`.
  BP384/BP512 are not registered (no BP512 crate exists; no TI interface needs them).
- **RSA is a data model only in milestone 1.** The names are registered as reserved, the
  `rsa` feature refuses to build (`just jwz-rsa-guard`).
- **Post-quantum names are reserved**: ML-DSA-44/65/87, ML-KEM-512/768/1024.
- **Layout: flat in the zero-lab `rust/` workspace** (`rust/jwz`, `rust/jwz-brainpool`,
  `rust/ti-jwz`), sharing its lock file, supply chain, deny configuration and Justfile.
  Tags follow the workspace convention `rust/<crate>/vX.Y.Z`. Because the shared
  `deny.toml` also governs `ti-cli`, whose TLS uses rustls with ring, backend purity is
  a tree check (`just jwz-backends`) rather than a deny ban. Moving jwz to a repository
  of its own later means moving three directories and adapting tags and tooling there.
- **Licence: Apache-2.0, gematik GmbH**, as for every crate in the workspace. All jwz
  crates stay `publish = false` until the crate name is confirmed with the maintainers.
- **Design time and build time are separate.** Building and `just check` need stable
  Rust only. Formal verification (Kani, hax/F*), interop fixture generation, fuzzing and
  browser round trips run at design time and commit their results with a stamp (the
  hash of their inputs and the tool versions); `just check` fails on a stale stamp, and
  `just jwz-recheck` re-runs only what changed (stage S7/S8).

## Auditability

Written for reviewers who are not Rust specialists: one security decision in one place
(algorithm acceptance only in `profile::Policy::check`, signature verification only in
`jws::verify`, key agreement only in `jwe::ecdh`); short straight-line functions; no
macro-generated logic beyond `compile_error!` and derives; explicit type-state instead
of "already checked" flags; every rule carries its source (`// RFC 7515 §5.2 step 8`,
`// gemSpec_Krypt V2.50.0 …`) and the test covering it names the same source; no panics
on input (`unwrap`, `expect`, `panic`, indexing denied outside tests); constant-time
comparison of MACs, tags and thumbprints; secrets in `Zeroizing`; every dependency
justified in `docs/dependencies.md`; randomness only through `Rng`, so every path is
reproducible in tests.
